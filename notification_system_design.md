# Stage 1 - API Design

## Assumptions

- Users are pre-authenticated by the campus identity layer. APIs receive trusted identity headers from an API gateway.
- No login, signup, public sharing, webhook forwarding, or external sharing logic is included.
- All services use a custom `LoggingMiddleware` that emits structured application events to the internal observability sink. Application code must not use `console.log`, framework default request loggers, or built-in logger shortcuts directly.
- Notifications are confidential campus records. Access is scoped to the authenticated student, campus admin, or service role.

## Common API Headers

| Header | Required | Description |
| --- | --- | --- |
| `X-Request-Id` | yes | Idempotent request trace id generated by gateway/client. |
| `X-User-Id` | yes for student APIs | Pre-authenticated student/admin identifier. |
| `X-User-Role` | yes | `student`, `admin`, or `system`. |
| `Idempotency-Key` | yes for writes | Prevents duplicate create/bulk notification jobs. |
| `Content-Type` | yes for bodies | `application/json`. |
| `Accept` | yes | `application/json`. |

## Real-Time Notification Mechanism

Use WebSockets for authenticated campus app sessions and Server-Sent Events as a simple fallback for browser-only clients.

- WebSocket endpoint: `GET /api/v1/realtime/notifications`
- Gateway validates pre-auth headers, then subscribes the connection to `student:{student_id}`.
- Notification workers publish compact events to Redis Pub/Sub or Kafka topic `notification-events`.
- Realtime service pushes only confidential in-app payloads to the owning student connection.
- Clients acknowledge event receipt with `notification_id` and `event_id`; duplicate events are ignored using event idempotency.
- Email delivery is handled asynchronously and never blocks WebSocket delivery.

# Stage 2 - Database Design

## Database Choice

Use PostgreSQL as the primary database.

Justification:

- Notification reads need strong per-student consistency for read/unread state.
- The data model has clear relational entities: students, campaigns, notifications, deliveries.
- PostgreSQL supports indexing, partitioning, JSONB metadata, transactions, read replicas, and mature operational tooling.
- At millions of notification rows, relational partitioning plus cursor pagination is sufficient and simpler than premature NoSQL complexity.

Redis is used for cache and realtime fanout state. Kafka or RabbitMQ is used for asynchronous delivery.

## Schema

```sql
CREATE TYPE notification_type AS ENUM ('Placement', 'Result', 'Event');
CREATE TYPE delivery_channel AS ENUM ('in_app', 'email');
CREATE TYPE delivery_status AS ENUM ('pending', 'sent', 'failed', 'retrying', 'dead_lettered');

CREATE TABLE students (
    id BIGINT PRIMARY KEY,
    department_id TEXT NOT NULL,
    batch_year INT NOT NULL,
    status TEXT NOT NULL DEFAULT 'active',
    email TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE notification_campaigns (
    id UUID PRIMARY KEY,
    name TEXT NOT NULL,

    body TEXT NOT NULL,

    created_by BIGINT NOT NULL,

CREATE TABLE notifications (
    id UUID PRIMARY KEY,
    campaign_id UUID REFERENCES notification_campaigns(id),
    student_id BIGINT NOT NULL REFERENCES students(id),
```

## API Queries

Fetch notifications:

```sql
SELECT id, student_id, notification_type, title, body, priority, is_read, created_at, read_at
FROM notifications
WHERE student_id = $1
  AND ($2::notification_type IS NULL OR notification_type = $2)
  AND ($3::boolean IS NULL OR is_read = $3)
  AND ($4::timestamptz IS NULL OR created_at < $4)
ORDER BY created_at DESC, id DESC
LIMIT $5;
```

Mark read/unread:

```sql
UPDATE notifications
SET is_read = $3,
    read_at = CASE WHEN $3 = true THEN now() ELSE NULL END,
    updated_at = now()
WHERE student_id = $1
  AND id = $2
RETURNING id, is_read, read_at, updated_at;
```

Create per-recipient notification rows:

```sql
INSERT INTO notifications (
    id, campaign_id, student_id, notification_type, title, body, priority, metadata
)
SELECT gen_random_uuid(), $1, s.id, $2, $3, $4, $5, $6
FROM students s
WHERE s.id = ANY($7::bigint[]);
```

Create delivery rows:

```sql
INSERT INTO notification_deliveries (id, notification_id, channel)
SELECT gen_random_uuid(), n.id, c.channel
FROM notifications n
CROSS JOIN unnest($1::delivery_channel[]) AS c(channel)
WHERE n.campaign_id = $2
ON CONFLICT (notification_id, channel) DO NOTHING;
```

## Scaling Issues and Solutions

- Large fanout writes can overload the primary database. Use queue-driven batch inserts, bounded worker concurrency, and campaign-level backpressure.
- Hot students or repeated page loads can create read pressure. Use Redis per-student cache, cursor pagination, and read replicas.
- Millions of old rows slow scans and maintenance. Partition by `created_at`, archive old partitions, and keep indexes local to partitions.
- Cohort targeting can scan the student table. Maintain cohort indexes and optionally materialized cohort membership for common segments.
- Realtime fanout can overload app servers. Use stateless WebSocket gateways backed by Redis/Kafka subscription routing.

# Stage 3 - Query Optimization

Given query:

```sql
SELECT *
FROM notifications
WHERE studentID = 1042 AND isRead = false
ORDER BY createdAt ASC;
```

## Correctness

The intent is correct: fetch unread notifications for one student ordered oldest first. In the proposed schema the column names should be `student_id`, `is_read`, and `created_at`. `SELECT *` should be avoided because it increases I/O and couples API responses to table shape.

Optimized query:

```sql
SELECT id, notification_type, title, body, priority, created_at
FROM notifications
WHERE student_id = $1
  AND is_read = false
ORDER BY created_at ASC, id ASC
LIMIT $2;
```

## Performance Issue

Without an index, PostgreSQL may scan all notifications for all students, filter by `student_id` and `is_read`, then sort by `created_at`. With millions of rows, this causes high CPU, memory sort cost, and disk reads.

## Indexing Strategy

For unread notifications:

```sql
CREATE INDEX idx_notifications_student_unread_created_asc
ON notifications (student_id, created_at ASC, id ASC)
WHERE is_read = false;
```

Why partial index:

- Most notifications eventually become read, so unread rows are a smaller working set.
- The index matches the equality filter and the ordering.
- The query can use an index range scan and avoid a full table sort.

## Cost Explanation

- Without index: approximately `O(N)` scan plus `O(M log M)` sort, where `N` is total notifications and `M` is unread notifications for the student.
- With matching partial index: approximately `O(log U + K)`, where `U` is unread indexed rows and `K` is returned rows.
- Write cost increases because unread inserts add index entries and read updates remove them from the partial index.

## Should Every Column Be Indexed?

No. Every index consumes disk, memory, and write throughput. Inserts, updates, and deletes must maintain each index. Too many indexes also make query planning slower and increase operational maintenance. Index columns that match frequent filters, joins, sort orders, uniqueness rules, or high-value partial predicates.

## Students Who Got Placement Notifications in Last 7 Days

```sql
SELECT DISTINCT student_id
```


# Stage 4 - Performance Improvement

Problem: the database is overloaded because every page load fetches notifications.

## Redis Caching

Cache the first page and unread count per student:

- Key: `notifications:student:{student_id}:type:{type}:page:first`
- TTL: 30-120 seconds with jitter
- Invalidate or update on notification create/read-state changes

Trade-offs:

- Faster reads and lower DB load.
- Cache invalidation adds complexity.
- Short TTL may still cause bursts; long TTL may show stale read state.

## Pagination

Use cursor pagination instead of offset pagination.

Trade-offs:

- Stable under inserts and efficient with `(student_id, created_at, id)` index.
- Cursor state is less human-readable than `page=3`.
- For admin exports, background jobs are better than huge pages.

## Lazy Loading

Load the first page immediately, then load older notifications when the user scrolls or clicks next.

Trade-offs:

- Reduces unnecessary data transfer.
- Requires loading states and careful accessibility behavior.
- Users searching old data may still trigger multiple requests.

## Event-Driven Updates

Use WebSockets/SSE to push new notification events. Clients update local state instead of refetching on every route change.

Trade-offs:

- Low latency and fewer polling reads.
- Requires connection management, heartbeats, reconnect logic, and idempotent event handling.
- Mobile or unstable networks need fallback polling.

## Read Replicas

Route notification list reads to replicas and writes to primary.

Trade-offs:

- Protects the primary database from read bursts.
- Replica lag can briefly show stale read/unread state.
- Read-your-write behavior may require primary reads for a short window after mutation.

# Stage 5 - System Design at High Scale

Given pseudocode:

```text
for each student:
    send_email()
    save_to_db()
    push_to_app()
```

## Problems

- It is blocking and sequential; one slow email call delays every later student.
- A failure midway leaves inconsistent delivery state.
- There is no retry, dead-letter handling, idempotency, or backpressure.
- Email, database, and in-app push are tightly coupled.
- The loop cannot safely handle 50,000+ students or millions of rows.
- There is no observability beyond forbidden built-in logging.

## Redesign

Use asynchronous fanout with durable queues.

- API creates a campaign and publishes `CampaignCreated`.
- Fanout workers resolve recipients in batches and publish `NotificationRecipientBatch`.
- Persistence workers bulk insert notification rows and delivery rows.
- Email workers consume `EmailDeliveryRequested`.
- Realtime workers consume `InAppDeliveryRequested`.
- Retry policies use exponential backoff with jitter.
- Dead-letter queues retain permanently failed delivery tasks for inspection.
- Idempotency keys prevent duplicate campaign creation and duplicate per-recipient delivery.

## What if Email Fails Midway?

The email delivery row is marked `retrying` with `attempt_count`, `last_error`, and `next_retry_at`. The in-app notification remains available because it is persisted separately. After max retries, the email delivery moves to `dead_lettered` while the notification itself remains in the database.

## Should DB and Email Be Coupled?

No. Database persistence is the system of record. Email is a delivery channel. Coupling them creates partial failures and slow user-facing writes. Persist first, then request channel delivery asynchronously using an outbox or queue event.

# Stage 6 - Priority Notifications

## Requirement

Return the top 10 notifications from:

`http://20.207.122.201/evaluation-service/notifications`

Constraints:

- Do not store data in the database.
- Do not hardcode notifications.
- Efficiently maintain the top 10 using a heap/priority queue.
- Do not use `console.log` or built-in loggers. The runnable implementation uses `LoggingMiddleware` and writes command output through `process.stdout.write`.

## Working Code

The working implementation is provided in `stage6_priority_notifications.js`.

Run:

```bash

```

If the evaluation service requires authorization, provide the token without changing source code:

```bash

```

Code:

```javascript
const API_URL = "http://20.207.122.201/evaluation-service/notifications";
const PRIORITY_WEIGHT = { Placement: 3, Result: 2, Event: 1 };

class LoggingMiddleware {
  constructor() {
    this.events = [];
  }

  record(eventName, details = {}) {
    this.events.push({
      eventName,
      details,
      timestamp: new Date().toISOString()
    });
  }
}

class MinHeap {
  constructor(compare) {
    this.items = [];
    this.compare = compare;
  }

  size() {
    return this.items.length;
  }

  peek() {
    return this.items[0];
  }

  push(item) {
    this.items.push(item);
    this.bubbleUp(this.items.length - 1);
  }

  replaceTop(item) {
    this.items[0] = item;
    this.bubbleDown(0);
  }

  toSortedArray() {
    return [...this.items].sort((a, b) => this.compare(b, a));
  }

  bubbleUp(index) {
    while (index > 0) {
      const parent = Math.floor((index - 1) / 2);
      if (this.compare(this.items[index], this.items[parent]) >= 0) break;
      [this.items[index], this.items[parent]] = [this.items[parent], this.items[index]];
      index = parent;
    }
  }

  bubbleDown(index) {
    while (true) {
      const left = index * 2 + 1;
      const right = index * 2 + 2;
      let smallest = index;

      if (left < this.items.length && this.compare(this.items[left], this.items[smallest]) < 0) {
        smallest = left;
      }

      if (right < this.items.length && this.compare(this.items[right], this.items[smallest]) < 0) {
        smallest = right;
      }

      if (smallest === index) break;
      [this.items[index], this.items[smallest]] = [this.items[smallest], this.items[index]];
      index = smallest;
    }
  }
}

function getNotificationType(notification) {
  return notification.notification_type || notification.type || notification.Type || notification.category || "Event";
}

function getCreatedAtMs(notification) {
  const rawDate = notification.created_at || notification.createdAt || notification.Timestamp || notification.timestamp || notification.date;
  const parsed = Date.parse(rawDate);
  return Number.isNaN(parsed) ? 0 : parsed;
}

function comparePriority(a, b) {
  const typeDiff =
    (PRIORITY_WEIGHT[getNotificationType(a)] || 0) -
    (PRIORITY_WEIGHT[getNotificationType(b)] || 0);

  if (typeDiff !== 0) return typeDiff;
  return getCreatedAtMs(a) - getCreatedAtMs(b);
}

function extractNotifications(payload) {
  if (Array.isArray(payload)) return payload;
  if (Array.isArray(payload.data)) return payload.data;
  if (Array.isArray(payload.notifications)) return payload.notifications;
  return [];
}

async function fetchNotifications(loggingMiddleware) {
  loggingMiddleware.record("stage6.fetch.started", { apiUrl: API_URL });

  const headers = { Accept: "application/json" };
  if (process.env.NOTIFICATION_API_TOKEN) {
    headers.Authorization = `Bearer ${process.env.NOTIFICATION_API_TOKEN}`;
  }

  const response = await fetch(API_URL, {
    headers
  });

  if (!response.ok) {
    throw new Error(`Notification API failed with status ${response.status}`);
  }

  const payload = await response.json();
  const notifications = extractNotifications(payload);
  loggingMiddleware.record("stage6.fetch.completed", { count: notifications.length });
  return notifications;
}

function topNotifications(notifications, limit = 10) {
  const heap = new MinHeap(comparePriority);

  for (const notification of notifications) {
    if (heap.size() < limit) {
      heap.push(notification);
      continue;
    }

    if (comparePriority(notification, heap.peek()) > 0) {
      heap.replaceTop(notification);
    }
  }

  return heap.toSortedArray();
}

async function main() {
  const loggingMiddleware = new LoggingMiddleware();

  try {
    const notifications = await fetchNotifications(loggingMiddleware);
    const topTen = topNotifications(notifications, 10);
    process.stdout.write(`${JSON.stringify(topTen, null, 2)}\n`);
  } catch (error) {
    loggingMiddleware.record("stage6.failed", { message: error.message });
    process.stderr.write(`${JSON.stringify({ error: error.message }, null, 2)}\n`);
    process.exitCode = 1;
  }
}

main();
```

## Approach

Each notification receives a comparison score from two dimensions:

- Type priority: `Placement > Result > Event`
- Recency: newer notifications rank higher within the same type

A min-heap of size 10 keeps only the current best notifications. For each incoming notification, compare it with the weakest item in the heap. Replace the weakest item only when the new item ranks higher.

## Time Complexity

For `n` notifications and top `k = 10`:

- Heap maintenance: `O(n log k)`
- Memory: `O(k)`

This is better than sorting all rows, which costs `O(n log n)` memory/time pressure for large responses.
